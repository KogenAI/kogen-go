# I4 — Repair and ladder wiring

## Component result

`internal/app/ladder_wiring.go` composes the resolved Build recipe with the
sequential ladder and hard-plan parallel controllers. The builder role comes
from `recipe.Load` and the resolved project manifest; escalation models stay
recipe-owned. Hard plans create separate rung sessions with the persisted
Build cache key, preserve both parallel outcomes in rung order, and continue a
dual-red result at the first remaining rung. Candidate refs, workspace names,
attempt order, failure summaries, and snapshots retain their global rung
identity after continuation. Candidate selection emits the fixed observational
audit fields and cannot make failed acceptance items landable.

Focused app tests cover role resolution, session separation and affinity,
dual-red continuation, stable global snapshots, audit advice preserving a
real green gate, and parallel winner cancellation/loser cleanup. The recipe
budget component continues to own the separate 10-minute landing allowance.

## Integration boundary

This worktree owns `ladder_wiring.go`, its tests, and this note; it does not own
`build_routes.go` or `status_routes.go`. At the I4 starting revision,
`newBuildRoutes` still constructs `single.Controller` directly and does not
provide a rung executor to this wiring. `status --watch` also still returns
the explicit “queue lifecycle ... in the Build integration round” error.
There is no safe call site within the owned files to connect this coordinator
to approval, run state, journal, and landing. Public ladder, report, and watch
behavior therefore remains open for the coordinator's integration handoff.

The component gate is code-ready evidence only. Do not count unwired
conformance cases as passing or as behavior conflicts. The exact frozen v1.2
run, its results, observed conflicts, and the shared-runner overlap are
recorded in `I4-repair-ladder-parity.evidence.md`.
